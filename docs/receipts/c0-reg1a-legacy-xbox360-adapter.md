> Registry coverage moves from **2/28 to 3/28 database units — in the working tree, uncommitted**.
> Asset-profile coverage is unchanged (1/14). Adding this adapter does **not** make NHL Legacy

## 6. Contract limitations found — for Codex's decision

None of these was worked around; each is recorded and the independent mappings continue.

1. **Capacity cannot express "measured on this platform's own save".** `source =
   "roster-save-max-records"` does not say *which* save; the Xbox 360 Legacy ROSTER save decodes but
   was never read, so the block is `derived` over the sha256 identity. Decision: whether reading that
   save (one number per table, seven tables) is C0 registration work or later measurement.
2. **A "same title, other file" enum anchor has no representation.** `defs/enums/handedness.toml`
   and `position.toml` anchor on an `NHL Legacy default.db` that is not in the repository. The
   contract offers only candidate-or-established; a named case confirming 0/1 and 0..4 against
   `anchors/xbox360/nhllegacy/databases/nhlng.db` would promote both, and with them the companion
   rule and the two rating applicability predicates (5 blocks). Decision: authorize that named case
   as a bounded measurement package, or leave the five blocks as candidates.
3. **`team.name` semantics rest on a metadata name plus engine source.** The contract's `derived`
   confidence covers it, but no audit states that `kOtt.fullname` is the club's display name. If
   Codex considers a metadata-name derivation insufficient for an *operative* mapping, the mapping
   should move to `blocked` with the identification as a candidate — it validates either way.
4. **Main-team origin is probe-only.** `Capabilities::main_team_offset` documents the answer for this
   title but nothing asserts it on this anchor; a one-assertion named case would promote the
   transform (and with it the foreign key's origin). Same decision class as 2.
