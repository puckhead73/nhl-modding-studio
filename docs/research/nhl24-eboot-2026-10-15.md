# NHL 24 executable logic research — 15 October 2026

The [expanded follow-up](nhl24-expanded-logic-2026-10-15.md) covers head/portrait
assignment, slider semantics, ONES, stat credit, simulation, capacities and All-Star
events. The accepted maximum is now 48 teams; work beyond that ceiling is dropped.

This investigation establishes concrete patch sites, build-specific tuning bindings,
and several structural limits. **It does not complete or enable all ten requested
features.** No game session was run, no installed game/patch/save file was changed,
and no new Studio application feature is claimed. The most advanced result is a
pressure-rating patch tested by executing the isolated original and modified machine
code with synthetic inputs on both builds. League expansion beyond 48, additional
league definitions, historical short-roster gameplay, and multi-team Franchise
control remain engineering and runtime-validation work.

## Executables and address conventions

| Build | Source | Bytes | SHA-256 |
|---|---|---:|---|
| 01.00 | `F:\Games\NHL 24\game\eboot.bin` | 187,071,493 | `0118720c7e0338e20769063437be5656d1c16262c6b81a688adb659582544e17` |
| 01.60 | `F:\Games\NHL 24\game-UPDATE\eboot.bin` | 188,338,041 | `fe5dcab197256487dd47906a4b0e0601bfe77fac9f47ad3f4f91b03b9372deb9` |

Both are plaintext-payload PS4 SELF containers containing x86-64 ELF images
(`ET_SCE_DYNEXEC`, entry 0x80), not ordinary Windows PE executables. There are 10
SELF records, five payload records and 12 ELF program headers. Extraction here is
container mapping, not decryption. Five payload-backed ELF segments were reconstructed
for offline analysis. The trailing non-payload program header is not reconstructed;
Ghidra reports that range as invalid and reports unavailable dynamic-table information.
Decompilation therefore does not establish complete import/relocation semantics.

All addresses below are **guest image virtual addresses**, before the host load base.

* Instruction SELF offset in base = image VA + `0x51400`.
* Instruction SELF offset in update = image VA + `0x51d80`.
* Those formulas apply to the first mapped segment only. Other segments require
  their own program-header/SELF-record mapping.
* shad patch XML address = image VA + `0x400000`.
* Host process address = actual module load base + image VA. Do not hardcode it.

The installed `user/patches/nhl24.xml` and the existing `user/log/shad_log.txt`
corroborate this convention: the update replay patch uses XML `0x068E0770` for
image `0x064E0770`, and the recorded host patch address is `0x0e3f0770` with module
base `0x07f10000`. These are **previous installed-run observations**, not a fresh
run of our experiments. That log identifies CUSA37933, 01.60, NHL24 PC v0.8.1,
shadPS4 v0.19.1 WIP, commit `7ce4ce83-dirty`.

## Findings in requested priority order

### 1. Teams per league: small historical leagues through 48 teams

**Scope update, 15 October:** the user accepted 48 teams as sufficient. Expansion
to 49/50 is no longer an implementation target. The overflow findings below remain
as evidence for enforcing the accepted ceiling.

**There is a real 48-team structural boundary, not merely a UI maximum.**

Update `0x08977d00`, called by the custom league structure generator
`0x08976ea0`, contains two insertion paths:

| Instruction | Observed operation |
|---|---|
| `0x08977e04`, `0x08977fa1` | Compare existing count against 47; skip insertion if greater |
| `0x08977e11`, `0x08977fae` | Write team identifier at `object + 4 + index*4` |
| `0x08977e18`, corresponding second path | Write associated value at `object + 0xc4 + index*4` |
| `0x0833868b` | Stock NHL-team population also guards index against 47 |
| `0x0815b65f` | Custom setup addresses these objects with stride `0x184` |

This establishes the observed block shape: a 4-byte count and two arrays of
48 4-byte entries, totaling `4 + 48*4 + 48*4 = 0x184` bytes. In the league creator,
blocks start at `+0x1b18`; related structures are addressed at `+0x2430` with
stride `0x60`. Six `0x184` blocks exactly span that interval. This is a creator
layout observation, **not a claim that the entire game supports only six leagues**.

Changing only the comparison to admit team 49 would write its identifier into
the first associated-value slot; its associated value would land at the next
block boundary. A 50-team equivalent needs at least a `0x194` block and second
array offset `0xcc`, plus changes to all owners, copies, indexing, serialization,
schedule generation and consumers. No 50-team patch is supplied.

For small leagues, the generic custom builder already receives team count,
conference/division parameters and distributes quotient/remainder counts. It is a
better starting point than the stock NHL default-team path, which still explicitly
iterates 32 entries at `0x08338682`. The minimum accepted count in the UI/configuration
schema has **not** been resolved; four-/five-team creation, schedules, playoffs and
season rollover have not been tested. EA documented a 6–48 custom-league range for
[NHL 23's mode design](https://www.ea.com/de-de/games/nhl/amp/news/game-modes-deep-dive).
That historical documentation is context, not independent NHL 24 qualification.

The update settings bridge binds `League_TeamsInLeague` to setting ID `0x4e8`
at `0x04f298e0`/`0x04f298f8`. The named input `TeamsInLeague` is converted from
a numeric value and passed to the settings setter with that ID at
`0x0373b839`–`0x0373b84b`; named read/default paths occur at `0x0382f048`
and `0x03841ee5`. This is a concrete configuration binding, not a recovered
minimum/maximum declaration. The bridge obtains metadata through virtual calls;
the scalar ID is not itself the team count. Other occurrences of immediate
`0x4e8` in allocator paths are allocation sizes and must not be patched as settings.

Next implementation target: expose the existing custom builder within verified
capacity and qualify 4/5/6 and 45/48 separately. Required
fixtures include odd team counts, byes, uneven divisions, no affiliates, playoffs,
save/reload, and the following season. A single successful exhibition is insufficient.

### 2. Additional leagues: KHL, USHL, NCAA and others

An existing debug setting is located and traced:
`Enable leagues outside of modes they were intended for (ex. IIHF in create team or roster moves)`.

| Build | Initializer immediate VA | Original → experiment |
|---|---|---|
| 01.00 | `0x0267574a` | `00` → `01` |
| 01.60 | `0x025fafaa` | `00` → `01` |

On 01.60 the registration object is `0x0baa7020`, default byte `+0x38`, runtime
object pointer slot `+0x40`. Consumers dereference that pointer and test runtime
byte `+0x29`; writing the registration default after startup would not be equivalent.
Consumer `0x04fe0c50` combines mode-name checks with this runtime boolean.
Other references occur in `0x03df28e3`, `0x04479e24` and nearby paths.

This is an **existing-league eligibility experiment**, not an additional-league
implementation. It does not allocate IDs, create DB relations, add frontend choices,
or construct a new mode. League construction uses dedicated defaults for NHL, AHL,
ECHL, European leagues and tournaments; the large default builder starts at
`0x083384d0`. `LeagueFactory::_LoadLeagueType` at `0x081770c0` also contains a
mode dispatch and a six-entry tiers allocation. Its dispatch range is not proof of
a global league-ID maximum. No single authoritative global league-count constant
has been identified.

Required work: determine the league-ID registry and all enum/schema consumers,
add league/team/membership/rule/schedule/localization/presentation data, then extend
the relevant mode factories. Existing IDs should not be silently repurposed if
the requested outcome is genuinely additional leagues.

### 3. Short rosters: 8–10 skaters

At update `0x03e0e190`, a routine constructs a named roster-limits object:

| Named property | Observed value | Value instruction |
|---|---:|---|
| `MaxPlayableRosterSize` | 23 | `0x03e0e2db` |
| `MinNumberOfPlayableGoalies` | 2 | `0x03e0e2ef` |
| `MinNumberOfPlayableSkaters` | 18 | `0x03e0e303` |
| `MinPlayableRosterSize` | 20 | `0x03e0e317` |
| `MaxTotalRosterSize` | 27 | `0x03e0e32b` |

Separately, `0x033fc230` publishes `TeamMinSkaters = 18` at `0x033fcb6d`,
alongside goalie/skater maximums. `0x04875250` copies the named roster-limit
properties between objects. The roster validation service is present as
`nhl-data:team:roster:is-valid:get:01.00.00`; references were located in
`0x03904a90`, `0x04867dd0`, `0x04868130`. Error mapping at `0x03914220` distinguishes
too few dressed skaters/goalies in pro and minor contexts.

These are concrete frontend/data-service restrictions, **not proof that changing
four numbers yields safe gameplay**. Still unresolved: actual engine lineup
requirements; duplicate/empty line slots; power-play/penalty-kill and special lines;
injury/ejection/fatigue replacements; emergency goalie handling; simulation;
automatic roster repair and Franchise minimum-contract requirements.

Implement as a coupled historical-roster policy: skater minimum, goalie minimum,
total minimum, line construction, roster repair and simulation all need the same
policy. Preserve the upper capacity. Do not simply bypass validation or fill absent
players with invalid IDs. No short-roster patch is exported at this evidence level.

### 4. Franchise/Dynasty features with full league control

The executable contains both shared mode-creation machinery and separate Season/
BeAGM configuration layouts. `ModeCreationUserTeams::InfoSet` is located at
`0x04566830`; it handles pro/minor custom subgroup names and Franchise submode input.
The league creator allocates a per-team `FeTeamControlType` array dynamically from
the team count (`0x0815b5d0`, `0x0815bf50`), initializes its entries to zero, and
keeps pointers at creator `+0x2cb8 + tier*8`. `0x03e4acb0` derives `NumUserTeams`
from a `UserTeamList` used by Season save metadata.

This shows useful shared infrastructure; it does not prove multi-GM Franchise
support. `TmCtrl1`, `TmCtrl2`, `UserTm`, `RosterCtrl`, `Trades`, `CpuTrd`, `GmFire`
and `EnforceLines` are setting names registered by `0x04fd7c30`. Their names alone
do not establish bitmask widths or storage semantics.

Recommended direction: retain Franchise as the simulation base and extend team
selection/active-team context and permission checks. Moving its entire offseason,
contract, draft and progression systems into Season is a larger dependency change.
The recommendation is architectural, not a verified patch recipe. Trace singular
GM/owner state, active-team routing, transactions, inboxes, drafting, AI automation,
calendar advancement and save/reload before advertising full league control.

### 5. Historical rules

Two-line-pass infrastructure exists: `TwoLinesOffside`, `Rule_TwoLinesOffside`,
`TwoLineRuleIsOn`, `NhlWhistle_TwoLinePass` and delayed whistle-reaction tuning.
The rule-name accessor is `0x031a73e0`; the nearby predicate at `0x031a7420`
tests a context field at `+0x7e0`, returning zero unless its enum value is 1 or 2.
The initializer references at `0x03181a11`/`0x03181a77` associate this neighborhood
with `TwoLineRuleIsOn`. Named rule serialization/configuration references occur at
`0x0253c9d9`, `0x03723c0b`, `0x0374136d`, `0x04f712ba`.
The update metadata bridge binds `Rule_TwoLinesOffside` to setting ID `0x90d`
at `0x04f712d2`; the named `TwoLinesOffside` input setter uses the same ID
at `0x037413a9`. These IDs are update-build observations, not assumed stable
cross-version enums.

This supports pursuing re-exposure of an existing rule. The enum meanings, actual
whistle trigger and AI adaptation are not yet fully traced. Do not force the
predicate to true as if that alone implements two-line-pass enforcement.

No equivalent historical no-forward-pass switch was identified. Matches such as
`gForwardPassBias*` concern AI pass preference; `NoForwardDepthPass` is rendering.
A true rule needs pass release/last-possession tracking, attack-direction-normalized
coordinates, recipient/touch classification, whistle/faceoff decisions and AI
legality scoring. Historical year/zone exceptions should be explicit rule policy.
Search non-matches here do not prove the code contains no dormant implementation.

### 6. New leagues in Franchise

The existing `FranchiseCustomLeagues` paths provide configuration, playoff validation
and custom structure construction, including:

* `0x0345f270`: playoff-team information with minimum/maximum playoff-team properties.
* `0x03acc480`: playoff tiebreaker checks.
* `0x03ad0a10`: dynasty games/breakdown checks.
* `0x0815b800`: custom realignment.
* `0x08976ea0`: default custom league team structure.

These support replacing/customizing the principal competition; adding independently
simulated KHL/NCAA/USHL leagues to one Franchise world is a separate objective.
It requires tier/affiliate policy, cross-league contracts/transfers, eligibility,
draft sources, schedules, statistics, progression and save serialization. The
observed creator's fixed tier blocks are relevant constraints; the actual mode-wide
concurrent league capacity remains unresolved. The debug eligibility toggle is not
a shortcut around this work.

### 7. New strategies

Database strategy loading and coaching application are located:
`ExhibitionStrategies::Init` (`0x03842730`), `LeagueStrategies::Init`
(`0x03864f80`), `CoachStrategy::ApplyHeadCoachStrategy` (`0x0865b9c0`) and
`FEINTERFACE::FETEAMDATA::LeagueTeamStrategy` (`0x081b97b0`). Named tweakables expose
breakout, forecheck, defensive/offensive pressure, special teams and assistant-coach
decisions.

Editing existing strategy parameters is feasible as a tuning operation. A new
strategy identity/behavior requires enum/schema/UI/serialization changes plus
AI selection and action/position scoring. A new dropdown label or duplicated data
row is not evidence of a new executable strategy. The compiled strategy dispatch
and full asset relationships have not yet been recovered.

### 8. AI: pokechecking, pressure, dekes

| `gMimicPCBaseChanceForFancyDekesBySkillLevel` | `0x0aa4f430` | .2, .5, .7, .9, 1 | `0x0271b6e0`, function `0x0271b0d0` |

The defensive-pressure consumer computes an index clamped to 0–4, reads one float
from its runtime array, then multiplies an existing pair of scores. This is stronger
evidence than a string hit, but the exact upstream index-to-difficulty mapping and

automatically equivalent to every pokecheck animation/decision path.

Do not start with goalie `gOverallPokeCheckTendency` just because its name resembles
the skater symptom. Also distinguish behavior intent from animation availability,
action arbitration, risk penalties, cooldowns and tuning overridden by game mode.
Test one intervention at a time with fixed teams, difficulty, sliders and gameplay
conditions; measure attempts, legal attempts, successful checks, penalties, pressure
distance and deke families rather than judging a single match impression.

### 9. Pressure system

**A narrow, executable-tested patch is available for the traced rating multiplier.**

The attribute getter starts at base `0x0282f440` / update `0x027b5ec0`. Its relevant
tail reads player state `+0x780`, takes the pinned multiplier for state 1, takes the
adrenaline multiplier for state 2 only when attribute ID is 8 or 15, otherwise uses
1.0. It multiplies the accumulated rating, truncates to an integer, and clamps to
36–99. Earlier branches exclude some attribute/context cases; this is not claimed
as the universal formula for every rating in the game. Attribute names for IDs 8
and 15 have not been qualified.

Measured defaults: `gPinnedRatingMultiplier = 0.8`,
`gAdrenalineRatingMultiplier = 1.05`. Their update runtime pointer slots are
`0x0b880ce0` and `0x0b880c90`; consumers read float `+0x34` from the pointed object.

The experiment replaces `cmp eax,1; je pinned` with `xor eax,eax; nop; nop; nop`.
The existing neutral 1.0 load then executes, and the subsequent comparison skips
the state-specific multiplier. It preserves the remaining arithmetic/clamping.

| Build | Patch image VA | SELF offset | XML address | Original → replacement |
|---|---|---|---|---|
| 01.00 | `0x0282f914` | `0x02880d14` | `0x02c2f914` | `83f8017422` → `31c0909090` |
| 01.60 | `0x027b6394` | `0x02808114` | `0x02bb6394` | same |

Validation executed the isolated machine-code block with relocated synthetic data:
5 states × 32 attribute IDs × 131 input ratings = **20,960 cases per build**.
Both stock and patched results were checked, totaling **83,840 comparisons** across
the two builds. The stock result matches its float32 multiplier/truncation/clamp;
the patched result matches neutral multiplication and the same clamp.

This does **not** qualify the entire pressure system as disabled. Separate evidence
includes `gAdrenalineEnergyLossMultiplier = 0.5`, goalie pinned-state save tuning,
pressure accumulator `0x0284d0a0`, and presentation/audio pressure events. Meter
durations and step-size controls also exist. Runtime reset/transition behavior and
all stamina/goalie consumers remain to be addressed for a complete disable option.

### 10. Attribute-rating influence

Besides the effective-rating getter above, `0x02fe6050` consumes the attribute
curve family and constructs lookup data. Three file-backed 11-point tables are
located: `gAttribCurve0` at `0x0aa514a0` (all .7), `gAttribCurve5` at
`0x0aa514d0` (0,.1,…,1), and `gAttribCurve10` at `0x0aa51500`
(0,.01,.04,…,1). Those shapes are observed; the complete interpolation/slider
formula is not yet reconstructed.

`gUsePerAttribCurve` is a float, initialized to 0 with declared maximum 1, **not a
boolean just because its name starts with “Use”**. The consumer compares a float
and caches an enable flag. `gPlayerAttribCurve` and `gGoalieAttribCurve` each
register 29 points in non-file-backed storage; consumers convert entries to integer
selectors. Treating those as ordinary arbitrary continuous gain curves would be
wrong. Their initialization/lifetime and selector ranges need qualification.

Other contextual remaps exist for human/CPU passing and awareness, fatigue, traits
and goalie logic. A global rating-strength slider should expose its actual scope;
it cannot promise every downstream mechanic changes uniformly.

## Tweakables provenance and build migration

The previous [CSV review](frostbite-2026-10-14/gameplay-tweakables-review.md) accurately
left the CSV unbound. This investigation additionally inspected the user-supplied
`Reference/New folder/NHL24Kit-2026-10-15.zip`, whose `gameplay_catalog.json` declares
CUSA37933 01.00, executable size, object IDs, initializer operands and original bytes.
The kit's README states it emits emulator patches and requires the 01.00 executable.

* The JSON has 21,666 records and 21,115 distinct names; all distinct names occur in
  the CSV. This associates the sources, not every CSV field with runtime truth.
* 21,635 file-backed original sites exactly match base bytes. The remaining 31
  array sites lie outside file-backed memory; zero values there were not verified
  as effective runtime defaults.
* Its `at` field is already image-relative. Subtracting its `meta.base` produces
  incorrect addresses; `0x400000` belongs to the XML conversion step.
* Scalar porting matched exact labels and normalized initializer instruction
  sequences: **19,108 unique static matches**, 195 ambiguous, 1,543 unmatched.
  The 820 arrays were handled separately.
* Of the unique scalar matches, 28 load payloads differ between base/update. Do not
  restore the base catalogue's defaults into an update or call its values current.
* Array registration matching resolved **624 unique storage bindings**: 596
  file-backed and 28 non-file-backed; 32 ambiguous and 164 unresolved.
* Curve bindings establish count, data pointer and consumers, not universal
  interpolation, axis units, editability or independence from other objects.

Crucially, scalar `load4`/`load8` patch sites are **RIP displacements**, not float
values. Writing `1.0` into the displacement would redirect the load incorrectly.
Among 12,970 matched load records, only 3,768 distinct constant-source addresses
occur; 10,691 records share their starting constant address with another record.
Patching those pooled constants in place could change unrelated settings.

Preferred writer designs: initialization-site redirection to separately owned
constant storage, or an appropriately timed runtime registry edit using verified
object layout and lifecycle. Neither is implemented as a general writer here.
Integer/bool immediates can be simpler but still require exact site/type verification.
Missing, ambiguous and newly changed values must remain unavailable, not silently
mapped by name or by a global address delta.

## Research tools and retained evidence

[REA](https://github.com/morluto/rea) 6.5.0 was installed locally. Its
`inspect-with-objdump` invocation verified the reconstructed update ELF's x86-64
header with unchanged pre/post hashes. Ghidra 12.1.4 was downloaded from the official
NSA release and its prerequisites verified with REA. REA's documented
[Windows Ghidra boundary](https://github.com/morluto/rea/blob/main/docs/windows-ghidra-p0.md)
does not admit this ELF, so targeted decompilation used Ghidra directly.

16 selected function requests produced 15 decompilations and one timeout (the large
default league-team builder). Some output contains unresolved calls/control-flow
warnings; disassembly is retained and takes precedence over inferred C signatures.
This is targeted analysis, not a fully analyzed 300,000-function executable.

## Studio integration contract and remaining work

Keep this work under the existing DB-07 executable-tunables progression:
Located → Referenced → Runtime-observed → Effect verified → Editing qualified.
The new research supersedes only the earlier lack of executable binding for the
specifically matched records. It does not promote NHL 24 to a supported Studio target.

1. Add a build-bound read-only catalogue: exact SHA-256/title/version, object ID,
   source ordinal, raw name/display name/category, type, initializer site, stored
   default, runtime value when observed, units, aliases and evidence level.
2. Add an experiment/patch-plan layer separate from database edits: original-byte
   checks, typed patches, overlap checks, patch ordering, load-base conversion,
   existing-patch preservation, restore and a visible qualification status.
3. Qualify the narrow pressure getter and existing-league eligibility experiments
   in a copied installation/save fixture. Compare baseline and modified behavior;
   verify both boot and full match/save paths, then restore and reproduce baseline.
4. Prioritize custom-league creation within the accepted 48-team ceiling, then
   smaller-than-stock counts. Expansion beyond 48 is out of scope.
5. Implement short rosters as a complete policy, not a UI validation bypass.
6. Resolve additional league registration and Franchise control separately; do not
   represent the debug league switch as either feature.
7. Add verified scalar edits first, then the specific measured indexed AI curves.
   Keep general curves, selector tables and runtime-only storage distinct.

Runtime evidence is the present boundary. The session had no running NHL24 process,
and it did not create a controlled game/save test session. There is no evidence yet
that a new league, 50-team competition, 8-skater lineup, historical no-forward-pass
rule, new strategy or all-team Franchise mode works. Those remain explicit open
items, not completed features hidden behind a future UI task.
