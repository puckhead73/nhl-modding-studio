## Current position

We have broad physical database knowledge and narrower semantic/asset knowledge. Parsing a field, naming it, importing it canonically, assigning a different native ID, writing it and proving runtime behavior are separate capabilities.

- The current registry contains **27 database adapter files**. The latest attribution review distinguishes **24 attributed partial adapters and three representation-only entries**: NHL 19 PS4, NHL 20 PS4 and the NHL 07 PS3 research copy. Legacy Recompiled has no database adapter. These 28 registry units include a research copy; they are not the 27 shipping targets.
- Those adapters currently declare **8–10 mapped physical fields each**. NHL 21 declares **10 of 3,265 fields across 115 tables**, corresponding to eight canonical properties. A declared mapping can itself still be blocked or lack its exact inverse-write proof.
- The canonical schema currently declares only player and team entities: basic names, birth date, handedness, stored overall, speed, a team reference and canonical IDs. It does not yet represent the complete content required by the agreed builder.
- More knowledge exists in metadata, native editors, relationship/enum definitions and tests than these adapters contain. The unmapped remainder must not be described as entirely unknown. Nor does a matching field name prove identical semantics between games.
- Four real asset-family profile files exist: portraits, logos, jerseys and equipment. The latest AS7 registry accounting is one populated family, three represented families and three absent families: heads, audio and arenas. Here “populated” means some usable observations, not a complete output pipeline. Heads have separate research/converter work; arena art is stretch scope.

Sources: [canonical schema](../../defs/canonical/project-schema.toml), [NHL 21 adapter](../../defs/adapters/nhl21-ps4.toml), [REG5](../receipts/c0-reg5-early-generation-adapters.md), [REG4 attribution correction](../receipts/c0-reg4-r1-attribution-and-verification.md), [AS7](../receipts/c0-as7-asset-evidence-measurements.md).

Classification below: **research** means a fact remains unresolved; **mapping** means existing knowledge must be incorporated into the builder contracts; **verification** means a candidate/implemented behavior needs exact-target tests. A row may require all three. Neither file-level counts nor absence from a registry alone proves an engine limitation.

## Avoid reopening already-resolved work

- AS7's multi-chunk `chunkzip` failures were subsequently addressed by S1. The [S1 review](../validation/s1-review-and-s2a-dispatch.md) accepts the bounded decoder correction; do not list it as still unknown. This does not close LZX, archive writer or runtime qualification.
- AS7 opened and measured the PS3 patch archive. Older notes saying it has never been opened are stale; **lookup precedence** remains unknown.
- Existing texture codecs, native roster operations and source field metadata are reuse material. Their absence from a canonical profile is often mapping/integration work, not new format discovery.
- Standalone head conversion has active independent work. Studio registry absence does not mean no conversion knowledge exists; obtain the versioned handoff rather than rebuilding it here.
- Arena database fields belong in entity mapping; arena art authoring remains stretch scope. Do not make it a prerequisite for a team/roster builder.

## Recommended work order

1. **Inventory known semantics into the canonical model.** Start with the exact team/player/roster properties and assets exposed by existing editors. Enumerate references and unknowns; avoid an indiscriminate reverse-engineering campaign over every table.
2. **NHL 21 complete import slice.** Trace the Blues, all rostered players, required companions, logos, kits and portraits into Project IDs and managed assets. Record missing head/audio dependencies honestly; identity-only and supported partial asset imports must remain usable.
3. **NHL 11 contrast slice.** Run the same import against an identified platform/source and resolve encoding, relationship and identity differences. This directly tests the user's mixed-source workflow.
4. **NHL 21 remapped output slice.** Allocate different native IDs, rewrite the dependency graph, install and prove that menus/gameplay/save reload still select the correct entities and assets. This is the key builder knowledge gate.
5. **Expand target adapters and asset roles.** Complete required families, save modes and target-specific runtime tests; keep blocked targets visible in graduation reports.

Physical fields can be inventoried comprehensively now. A defensible percentage of “game understood” cannot be computed from the present counts: fields repeat across tables/targets, some are outside scope, and the hard gaps are often one relationship or lookup rather than hundreds of scalar fields.

For each subsequent research item, record: exact target/version; canonical entity/property; native tables/fields; read/write transforms; ID namespace and references; asset members and hashes; lookup precedence; source/mode/runtime capacity; missing fact; evidence source; implementation state; next experiment; acceptance result. This becomes the machine-readable knowledge backlog alongside the existing adapter/profile registry rather than a competing source of truth.
